# Build

1. Frame the unit in one message. State the stack: the existing capability the change uses (standard library, installed dependency, project API). A stack named by the task or by `AGENTS.md` is binding. State the budget: net added source lines, excluding tests, generated files, and lockfiles; a limit the user gives is binding, otherwise estimate it. State the check: the failing test or command that will pass. Write the frame in the shape of [assets/frame-and-result.md](assets/frame-and-result.md). Search manifests, imports, and call sites before proposing new code. When the approach is unproven or several designs compete, stop and run **figure-it-out**, which gates prototype and design. Done when stack, budget, and check are written.
2. Go red first. For a bug, reproduce it, then ask why until you reach the root cause; a guard that hides the symptom is not a fix. Grep every instance of the failing call. After a restart failure, suspect stale state first. For a feature, write the failing test whose name states the behavior. Run it and quote the failure. Done when the red run is shown and fails for the stated reason.
3. Subtract before you add. Delete dead code, one-caller wrappers, and redundant guards on the path first. A pure addition names what it removed, or says nothing needed removing.
4. Implement the smallest change, one unit at a time. Each unit ends at a passing check. Commit per unit when asked, and never commit red except the red-first test. Done when the check passes.
5. Prove it on the real artifact. Run the actual feature path and read the actual value. When verification fails, suspect the way you observed before the system. Script the check when you can. Done when the real run's output is quoted.
6. Audit. Count net lines with [scripts/net-lines.sh](scripts/net-lines.sh) `[base] [budget]` and report them against the budget; never reword the limit to fit. The code is the source of truth: behavior lives in test names and types, comments only state constraints the code cannot express, and you add no plan, ADR, or note that restates code. Done when the reply follows the result block of the template.
7. Proceed without asking on reversible work; present the result and the reasons. Ask only at a one-way door (force-push, delete data, send externally) or a product decision that changes scope or a public interface. When no one can answer, write your recommended answer down as an assumption, continue, and list it in the result.
